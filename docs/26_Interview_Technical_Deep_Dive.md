# 26 · Interview Technical Deep Dive

> 面试技术问答准备。每条只写四件事：当前实现、技术理由、局限、后续改进。
> 全部基于当前代码，不含未实现的功能，也不虚构生产经验。

**版本**：v1.0 · 2026-09-17
**适用**：BuildHealth V3.2（Phase 6B 完成 + 两轮工程强化）

---

## 1. Why did you build BuildHealth?

**当前实现**
既有建筑监测与更新决策平台原型。后端 FastAPI + SQLite，把监测数据经
「异常检测 → BHI → 风险分级 → 改造决策」四层确定性算法处理，再由 AI 层
解释结果。前端 React 8 个页面。

**技术理由**
选题来自专业本身：既有建筑存量在增长，检测依赖人工，而监测系统采到的
原始数值本身不构成决策依据。中间缺一层可解释、可复现的分析层。
我想做的是那一层，而不是再做一个看板。

**局限**
没有真实建筑数据，全部是模拟数据生成器产出的；也没有和任何检测机构
合作验证过参数是否贴近实际工程经验。

**后续改进**
接入真实监测数据格式，用实际工程案例反向校准阈值与权重。

## 2. Why is this not just a dashboard?

**当前实现**
看板只做呈现。这个项目的核心在后端四层算法：三种异常检测并行合并、
BHI 五维加权、四档风险分级含覆盖规则、RP-v1.0 优先级 + REC-v1.0 规则引擎。
前端每一处数字都能追到 API，没有一处是写死的。

**技术理由**
判据是「结论能否被复算和追溯」。给一个 BHI 分数，我能指出它由哪几个
维度、乘了什么权重、来自哪些异常；给一条改造建议，我能追到触发它的
传感器与告警。看板做不到这一点。

**局限**
当前的可解释性停留在「结果可回溯」，还没有做敏感性分析
（某个阈值变化会把多少建筑从 Attention 推到 Abnormal）。

**后续改进**
加一层参数敏感性面板，让参数调整的工程影响可见。

## 3. How does anomaly detection work?

**当前实现**
三种方法并行，`app/analytics/anomaly.py`：

| 方法 | 抓什么 | 参数 |
|---|---|---|
| 绝对阈值 | 突变 | 裂缝 0.20/0.30 mm · 倾斜 3.0/4.0 ‰ · 温度 40 ℃ · 湿度 85 % |
| 变化率 | 持续发展 | 各指标独立绝对变化量与相对百分比 |
| Z-score | 偏离统计规律 | 7 天滚动窗口 · \|z\|>4 异常 · \|z\|>6 HIGH |

检出结果按 `(sensor, metric, method, severity)` 在时间窗口内去重。

**技术理由**
单一方法都有盲区。阈值法抓不到缓慢发展；变化率法对噪声敏感；Z-score
需要足够历史样本。三种并行后用严重度去重，是覆盖度和误报率之间的折中。
Z-score 对用电和湿度关闭，因为这两个指标本身波动大，统计检验意义有限。

**局限**
去重窗口是固定时长常量，没有按指标特性区分；参数是原型值，
没有用真实工程案例校准过。

**后续改进**
按指标分别设定去重窗口；引入季节性分解处理温湿度。

## 4. Why use explainable methods?

**当前实现**
全部算法可手算复现：加权求和、比值、Z 检验。没有黑箱模型。
每个结果都带 `explanation` 字符串与 `calculation_version`。

**技术理由**
工程的结论要能被质疑和复核。如果给结构工程师一个无法解释的分数，
他不会用，也不该用。可解释性在这里不是加分项，是可用性的前提。
另外可解释的方法能被测试直接断言，回归保护强得多。

**局限**
可解释性与表达能力有取舍：纯加权模型难以捕捉维度间的非线性耦合。

**后续改进**
如需引入更复杂模型，必须同时提供可解释的近似或归因，否则不引入。

## 5. How is BHI calculated?

**当前实现**
`BHI = Σ (维度分 × 权重)`，范围 [0,100]：

| 维度 | 权重 | 输入 |
|---|---|---|
| Structural Safety | 0.40 | 结构类异常 |
| Facility Condition | 0.20 | 房龄 / 设计寿命 |
| Environmental Quality | 0.15 | 温湿度稳定性 |
| Energy Performance | 0.10 | 用电变异系数 |
| Fire Safety | 0.15 | 楼层 + 房龄（占位） |

维度输入超出 [0,100] 直接报错，不静默截断。

**技术理由**
权重反映「结构安全最要紧」的工程直觉，同时保留设施、环境、能耗、
消防四个维度，避免单一指标决定结论。输入越界报错是刻意选择：
静默截断会让错误数据看起来像正常结果。

**局限**
权重是工程判断，不是从数据里学出来的；消防维度目前是占位实现，
只用楼层和房龄，没有真实消防设施数据。

**后续改进**
用有标注的历史案例做权重校准；消防维度接入真实数据后重写。

## 6. Why are the weights prototype parameters?

**当前实现**
权重定义在 `app/analytics/config.py`，带版本号 `BHI-v1.0`，随 API 返回，
在参数端点 `GET /api/engineering-parameters` 公开，前端有专门的参数页说明。

**技术理由**
这些数字没有经过任何标准委员会或行业共识背书，是我基于工程常识定的。
把它们称为「标准」会误导使用者，也可能让系统被误用到它不该承担的场合。
所以显式标注为 Prototype Design Parameters，并在所有展示处说明。

**局限**
原型参数意味着不能直接用于真实决策，这是刻意的边界，不是待办事项。

**后续改进**
若要投入真实使用，必须由具备资质的工程团队评审并背书参数。

## 7. How does risk classification work?

**当前实现**
按 BHI 分四档：`≥90` Normal · `≥75` Attention · `≥60` Abnormal · `<60` HighRisk。
外加覆盖规则：只要存在 HIGH 严重度异常，最低升级为 Attention。

**技术理由**
覆盖规则处理「总分还行但有严重局部缺陷」的情形。BHI 是加权平均，
局部严重问题会被其他健康维度稀释。规则方向是保守的 —— 宁可多提醒，
不会漏报。风险分级的所有边界在参数端点公开，并用引擎行为测试锁定。

**局限**
四档边界是等距直觉划分，没有做风险分布的统计校准。

**后续改进**
用真实检测结论做分档校准；考虑引入随时间恶化的趋势项。

## 8. How does retrofit priority work?

**当前实现**
RP-v1.0：五个子分加权成 0-100 优先级
（风险严重度 0.35 · 趋势 0.25 · 构件重要性 0.20 · 紧急度 0.10 · 成本效益 0.10），
分档 Low / Medium / High / Very High。REC-v1.0 规则引擎按类目生成改造建议，
每条带成本等级与紧急度。建议实时计算，不落库。

**技术理由**
把「该不该先改这个」拆成可比较的维度，而不是给一个笼统排序。
成本效益独立成项，是为了让经济性和紧迫性分开表达。
不落库是因为它完全由当前数据决定，存下来反而会引入不一致。

**局限**
成本等级是经验分级，不是造价计算；不落库意味着没有历史版本可比对。

**后续改进**
接入造价数据把成本等级换成量化的成本区间；如需审计追溯则增加落库。

## 9. Why separate engineering evidence and knowledge evidence?

**当前实现**
两个独立字段：`AIResponse.evidence`（本建筑实测与派生数据）与
`AIResponse.knowledge_evidence`（项目内部知识库检索结果）。
prompt 里是两个独立 key，前端是两个独立分区（配色不同）。

**技术理由**
这是 RAG 系统最典型的失效模式：模型把「检索到的通用知识」说成
「本建筑的证据」。两者混淆在工程场景里后果严重 —— 用户可能以为
知识库里的某个概念描述就是这栋楼的实际情况。
分开之后，优先级也明确了：本建筑数据绝对优先，知识只做背景解释。

**局限**
字段分开能防止混淆，但不能阻止模型在自然语言里把两者混着说。
目前靠 prompt 指令 + 禁词扫描约束，属于缓解而非彻底解决。

**后续改进**
在答案生成后做一次归因检查，标出句子级引用来源。

## 10. Why use RAG?

**当前实现**
`backend/knowledge/` 5 篇手写 Markdown（异常检测、BHI、风险分级、
改造决策、工程红线），按 `##` 切成 23 个 chunk，TF-IDF + cosine 检索 top-3。

**技术理由**
没有 RAG 时，模型解释概念只能靠自己的通用知识，无法引用项目内部约定。
有了知识库，解释可以落在项目自己写定的定义上，且来源可查。

**局限**
知识库只有 5 篇，覆盖的是项目自身概念，不是广泛的工程知识。
它是「让解释有据可依」，不是「让系统变聪明」。

**后续改进**
扩充到工艺、材料、常见病害等领域文档（仍需人工评审后入库）。

## 11. Why not let the LLM calculate engineering results?

**当前实现**
AI 层只读 `EngineeringContext`（由确定性算法产出），不参与任何计算。
`context_builder` 严格只读不写库。AI 输出的 disclaimer 被后端强制覆盖，
`knowledge_evidence` 强制取自检索结果，模型自己返回的一律丢弃。

**技术理由**
三个原因：一是可复现，同样的数据必须得到同样的分数，LLM 做不到；
二是可审计，工程结论要能逐步复算；三是责任边界，让模型算分等于让
它承担工程判断，这不可接受。LLM 擅长的是把结构化结果讲成人话，
这是它该做的部分。

**局限**
模型的自然语言解释仍可能出现不准确的表述，靠 schema 校验和禁词
扫描只能拦住明确的越界表述。

**后续改进**
在解释层增加基于模板的结构化兜底，降低自由生成比例。

## 12. How does prompt injection protection work?

**当前实现**
四层防护：

1. system prompt 声明用户输入不可信，不得执行其中指令
2. 知识上下文单独声明不可信，且工程数据有绝对优先级
3. 输出经 Pydantic schema 校验，字段越界即失败
4. 43 条禁止短语扫描（含 11 条 RAG 专项），命中抛 `safety_violation`

**技术理由**
单靠 prompt 指令不够，模型可能被绕过。所以最后一道防线放在代码里：
无论模型说什么，输出必须过 schema 和禁词扫描。
`Mock` 与 `Real` 两个 provider 都走同一套运行时闸门。

**局限**
禁词是枚举式的，只能拦住已知表述；换一种说法可能绕过。

**后续改进**
补充基于语义的越界检测；对输出做引用归因校验。

## 13. Why use a deterministic retriever?

**当前实现**
纯 Python 标准库实现 TF-IDF + cosine，无向量库、无 embedding、
无外部服务。分类任务：语料 23 个 chunk，top-3。

**技术理由**
需求是离线、确定性、可解释。TF-IDF 的每次排序都能用 df/idf 数值解释，
测试可以直接断言；embedding 会引入模型下载、非确定性浮点和外部依赖。
在当前语料规模下，向量检索不会带来检索质量提升，只会增加基础设施。

**局限**
词形变化和同义词处理弱（"crack" 与 "cracking" 不互通），
中文按单字切分，语义粒度粗。

**后续改进**
加领域词表与轻量词干化；中文引入二元组切分提升粒度。

## 14. How would you scale the system?

**当前实现**
做过两轮批量化。第一轮把聚合接口从「逐建筑查询」改为固定次数的批量读取；
第二轮（Sprint 3）引入请求作用域分析复用并清掉剩余逐条查询。
3 栋建筑实测：

| 端点 | 起始 | 现在 |
|---|---|---|
| /api/dashboard/summary | 28 queries | 7 queries |
| /api/buildings/overview | 22 queries | 4 queries |
| /api/retrofit/overview | 64 queries | 6 queries |
| AI context build | 16 queries / 2 次异常检测 | 7 queries / 1 次 |

查询数不再随建筑数增长。

**技术理由**
起始形态是典型 N+1：循环里逐栋查最新评估（还查了两遍）、逐栋查传感器、
逐指标查监测序列，而且同一批序列被读三遍。批量读取 + 内存聚合是低风险解法，
API 契约完全不变。

**局限**
耗时瓶颈已经转移：92% 的响应时间是异常检测的 CPU 重算，查询只占很小一部分
（批量序列读取约 3 ms）。所以继续压查询收益有限。

**后续改进**
① 请求级共享（Sprint 3 已做）；② 把告警结果持久化，避免每次重算历史；
③ 建筑数上千时再考虑预聚合表或列式存储。刻意不引入缓存系统。

## 15. Where is the current N+1 issue?

**当前实现**
已基本清完。剩下的不是 N+1，而是两类不同的成本：

1. 不同 endpoint 各自重算异常检测。`/api/dashboard/summary` 与
   `/api/buildings/overview` 是两次独立请求，各自算一遍。
   这不是单次请求内的重复，而是跨请求的重复。
2. 单建筑端点（如 `/api/buildings/{id}/health`）每次请求重算一遍异常检测，
   用于写入新的 HealthAssessment。

**技术理由**
第 1 类要在无缓存前提下消除，就得把两个 endpoint 合并或提升为共享的
服务层，那会改变 API 形状；第 2 类是写路径的语义要求（重新计算才写入）。
两者都记录为技术债而不是硬做。

**局限**
当前 3 栋建筑无实际影响；上千栋时第 1 类会成为主要问题。

**后续改进**
第 1 类：把「取一次分析」提升为请求层的显式步骤，多个视图共享；
第 2 类：保持现状（写路径本就该重算）。

## 18. How did you identify and optimize the real performance bottleneck?

**当前实现**
两轮优化，每轮都是先测量再动手。

第一轮（Sprint 2）测的是数据库查询数。给 SQLAlchemy engine 挂
`before_cursor_execute` 监听器，逐端点数 SQL 语句：发现同一批监测序列
被读了三次、最新评估被查了两次、最近值逐传感器查询。批量化后
dashboard 28 → 7、overview 22 → 4、retrofit overview 64 → 13。

但批量化之后耗时几乎没变（dashboard 仍在 80ms 量级）。于是第二轮先做拆分
测量：单独计时异常检测与批量序列读取，结果是异常检测 80.0 ms、序列读取
3.0 ms —— **92% 的响应时间是 CPU，不是查询**。瓶颈已经转移了。

第二轮（Sprint 3）换了一个指标：不再数查询，而是数
`run_anomaly_detection` 的**调用次数**。结果是聚合端点本来就没有重复
（每栋建筑一次，已是理论最小值），真正重复的是 AI 链路：

```
build_engineering_context()
  ├── run_anomaly_detection()            ← 第 1 次
  └── get_retrofit_decision()
        └── generate_recommendations()
              └── run_anomaly_detection() ← 第 2 次（结果被丢弃）
```

引入请求作用域的 `BuildingAnalysis` 容器，一栋建筑算一次并沿调用栈传递：
AI context build 从 16 查询 / 2 次异常检测 / 59.0 ms
降到 7 查询 / 1 次 / 31.5 ms。retrofit overview 从 13 降到 6 条查询，
且不再随建筑数增长。

**技术理由**
关键是**先测量再优化**，而且**测量指标要跟着瓶颈走**。第一轮数查询是对的，
因为当时确实是查询问题；第二轮还数查询就会得出「没什么可优化」的错误结论，
因为瓶颈已经变成 CPU 重算。换成数「同一份计算被触发几次」才定位到真正的重复。

**为什么没有直接上 Redis**
三个理由：一是重复发生在**单次请求内部**，不是跨请求 —— 缓存解决的是另一个问题；
二是引入缓存要带来失效策略、一致性风险和第二份状态，而收益是 27 ms；
三是这是原型系统、单机部署、无并发压力，缓存的复杂度换不来对等收益。
用请求作用域的对象传递，代码量更小、语义更清晰、没有失效逻辑。

**局限**
- 跨 endpoint 的重复计算没有消除（dashboard 与 overview 各自算），
  不引入缓存就消不掉
- 单建筑写路径（health/recompute）本就该重算
- 耗时的绝对值不大（30-90 ms 量级），是在小数据集上测的；
  建筑数和记录数上去后分布会变

**后续改进**
把「取一次分析」提升为请求层的显式步骤，让多个视图共享同一份结果；
在更大数据集上重做基准，确认 CPU 占比与查询占比的变化趋势。

**等价性验证**
所有优化都要求「优化路径 == 原路径」。做法是对同一栋建筑分别跑
「传预加载」和「不传预加载」两条路径，逐字段比对 anomalies / health /
risk / recommendations / decision / context，唯一允许的差异是
`created_at` 墙钟时间（测试显式剥离并注明）。
守卫本身也做了变异测试：去掉传下去的 analysis，测试立刻报
`anomaly detection ran 2 times`。

## 16. How would you replace simulated data with real monitoring data?

**当前实现**
`backend/scripts/seed_data.py` 用确定性时间序列生成器造数据
（基线 + 趋势 + 周期波动 + 噪声 + 事件）。数据模型是通用的：
Building / Component / Sensor / MonitoringRecord，与具体数据源无关。

**技术理由**
数据模型刻意做成设备无关的：`Sensor` 有 `sensor_type` 与 `unit`，
`MonitoringRecord` 只有 `timestamp` + `value` + `quality_flag`。
这意味着接入真实数据主要是写一个 ingestion 适配层，
不需要动分析层。

**局限**
真实数据有几件事当前没处理：缺失值与异常值标记策略、
传感器离线与漂移、时区与时钟不同步、不同采样频率对齐。
`quality_flag` 字段已经预留，但还没有基于它的过滤逻辑。

**后续改进**
① 写 CSV / 标准时序协议的 ingestion 适配器；
② 用 `quality_flag` 过滤低质量记录后再进入分析；
③ 增加数据质量报告页，让使用者看到数据完整性。

## 17. What would you change for production deployment?

**当前实现**
当前是单机开发形态：SQLite 单文件、SQLite 无并发写保护配置、
CORS 只放行本地地址、无认证、无速率限制、AI 默认走 Mock provider。

**技术理由**
这些都是刻意的范围控制 —— 项目目标是验证工程分析链路，
不是做一套可运营的服务。把范围收窄才能把工程部分做扎实。

**局限**
直接上生产会有明确缺口：数据库并发、认证授权、密钥管理、
审计日志、AI 成本控制、异常告警。

**后续改进**（按优先级）
1. 换 PostgreSQL，加迁移管理
2. 加认证与项目级权限（工程数据通常按项目隔离）
3. AI 端点加速率限制与成本追踪
4. 加审计日志，记录谁在什么时候看了/触发了什么计算
5. 容器化 + 反向代理，配置密钥由环境注入

**但有一条不会变**：无论怎么部署，工程计算与 AI 解释的边界、
红线约束和免责声明都必须保留。这不是部署配置，是系统定义。
